# 里程存储

累计里程保存在 STM32F407ZET6 内部 Flash 的扇区 7（`0x08060000`，128 KiB）。GPS 任务按位移累加，每增加 100 m 追加一条记录。实现位于 `odometer_flash.c`，调用方是 `gps.c` 和 `main.c`。

车上不再使用 SD 卡：里程（`0x069`）和圈速（`0x06A`）随遥测发往 WirelessGateway，不需要车载日志；内部 Flash 没有卡槽接触不良，也不依赖上电时有卡。

两帧变化慢，不必跟着 50 ms 的速度帧发送：`0x069` 每 500 ms，`0x06A` 每 200 ms，圈数变化时两帧立即各发一次，一圈结束的数据不会等到下个周期。`0x301`、`0x067`、`0x068` 仍为 50 ms。周期常量在 `gps.c` 的 `GPS_CAN_STATUS_TICKS`、`GPS_CAN_LAP_TICKS`（单位为 50 ms 周期数）。

## 存储布局

- 链接脚本在 `Memory_Budget` 段断言程序镜像不超过 384 KiB，链接器因此不会把代码放进扇区 7。
- 扇区按 8 B 槽顺序写入：第 0 个字是里程（米），第 1 个字是它的校验值，共 16,384 槽。每 100 m 一条，约 1,638 km 写满一次。
- 校验字最后写入，写到一半掉电的槽校验失败。读取取最后一个校验正确的槽。损坏的槽只跳过，不复用；写入位置是最后一个非空槽之后。

## 启动

`main.c` 在 CAN 控制器启动之前调用 `Odometer_Flash_Init()`：

1. 扫描扇区，起始里程取最新有效记录，没有记录则为 0。
2. 扇区已写满，或只有无法识别的内容（旧固件残留、被中断的擦除）时，擦除整个扇区，再把最新里程写进槽 0。擦除期间 CPU 停转，时间为秒级，所以必须早于 CAN 启动和调度器；约每 1,600 km 出现一次，表现为开机延迟。
3. 擦除失败时，起始里程仍然正常显示，本次开机不再保存，下次开机重试。

GPS 任务在界面启动完成后通过 `Odometer_Flash_GetInitial()` 取起始里程，再开始累加。

## 运行

- 每增 100 m，`gps_odometer_process()` 调用 `Odometer_Flash_Save()`：写 2 个字，CPU 每个字停转数十微秒，不阻塞 GPS 的 DMA 读取。
- 写入前确认槽为空，写完清空数据缓存（F4 的编程不会更新缓存），再读回校验。
- 一个槽写失败时丢弃该槽，换下一个槽重试一次；仍失败则返回 0，`g_odometer_flash_save_fail_count` 加一，等下一个 100 m 再写。
- 运行中从不擦除。槽用完后拒绝保存并计入失败数，里程显示和 CAN 遥测不受影响；一次开机内不会用完。

## 异常与取舍

| 情况 | 结果 |
| --- | --- |
| 写入中掉电 | 该槽校验失败，下次启动用上一条记录，最多丢 100 m |
| 擦除成功、写回槽 0 之前掉电 | 里程回到 0。窗口约为一次扇区擦除时间，每 1,600 km 左右开机时才有；里程帧随遥测发出，上位机若有记录可对照恢复 |
| 擦除或编程失败 | 当次开机停止保存，显示继续；下次开机重试 |
| 用 ST-Link 正常下载 | 只擦程序用到的扇区，里程保留 |
| CubeProgrammer 选 Full chip erase | 里程清零 |
| 旧固件（超过 384 KiB）在扇区 7 的残留 | 首次启动自动擦除 |

只用一个扇区而非两个交替：当前固件约 242 KB，两个扇区会把程序区压到 256 KiB，余量约 19 KB，界面资源稍有增长就会链接失败。单扇区的代价是上表第二行的窗口。

## 诊断

`g_odometer_flash_save_fail_count`（保存失败次数）和 `g_odometer_flash_erase_count`（本次开机成功擦除次数）可在调试器中查看。

## 验证

`tools/run_firmware_tests.py` 的 `test_odometer` 用带 NOR 语义的 Flash 模拟（编程只清位，擦除置位），覆盖：

- 空扇区、重启后恢复、未初始化时拒绝保存。
- 校验字写到一半、编程失败、HAL 报成功但数据未写入。
- 残留数据扇区、写满后拒绝保存、下次启动擦除并带入最新里程、擦除失败后只读、擦除后写回失败。
- GPS 位移累加触发保存，保存失败时显示里程继续增加。

上板待确认：扇区 7 实际擦除耗时与开机延迟、掉电后里程恢复、正常下载不清除里程。
