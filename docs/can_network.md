# CAN 网络分工

本文说明车手屏所处的 CAN 网络：有哪两条总线、每条上谁收谁发、车手屏在其中承担什么。帧的字段、比例和范围以 [`vehicle-interfaces`](https://github.com/BITFSAE/vehicle-interfaces) 为准；本仓库的收发实现、超时和过滤器见 [CAN 接口](can_interface.md)；方向盘一侧见 [方向盘与车手屏](steering_wheel.md)。

## 两条总线

| 总线 | 车手屏接口 | 位率 | 上面的节点 | 车手屏的角色 |
| --- | --- | --- | --- | --- |
| 整车 CANB | CAN1（PB8 接收、PB9 发送） | 500 kbit/s | ECU、BMS、PDM、风扇控制器、胎温采集模块、BRT 踏板编码器、遥测网关等（中央库接口表及实车节点），以及车手屏 | 接收并显示整车数据；发送 GPS、里程、圈速；转发方向盘的驾驶模式请求；发送方向盘合并指令 |
| 方向盘专用总线 | CAN2（PB12 接收、PB13 发送） | 500 kbit/s | 方向盘按钮板和车手屏 | 只接收，不发送 |

CAN2 与 CANB 在电气上分开。方向盘的帧 ID 登记在中央库的 `Vehicle_CanB.dbc` 中，只是为了统一编号，它们不出现在 CANB 上。

## 车手屏在 CAN 上做的三类事

### 1. 接收 CANB 数据并显示

| 内容 | 帧 | 发送方 | 显示位置 | 无新帧后 |
| --- | --- | --- | --- | --- |
| 电池 SOC、总压、电流 | `0x4B0` | BMS | 右栏 | 2 s 后显示 `--` |
| 允许的放电/回收功率与电流（SOP） | `0x4A0`、`0x4A3` | BMS | 中栏车速下方 | 0.3 s / 1.5 s 后显示 `--` |
| 油门开度、油压（机械制动开度） | `0x305` | ECU | 中栏油门、机械制动条 | 1 s 后 `--` |
| 踏板转角（能量回收开度） | `0x001` | BRT25-C0M4096-RT1 | 中栏能量回收条 | 150 ms 后 `--`；未找到静止位时也显示 `--` |
| 四轮扭矩、转速、电机/逆变器/IGBT 温度、AMK 故障码、电机使能 | `0x502..0x509` | ECU | 底栏、右栏 TMAX | 1 s 后 `--` |
| 驾驶模式（ECU 回报） | `0x509` | ECU | 左栏模式色块 | 保持上一个模式 |
| 低压母线电压、电流、功率 | `0x5A0` | PDM | 右栏 LV | 1.5 s 后 `--` |
| 三路风扇转速与占空比 | `0x5A2` | 风扇控制器 | 右栏 | 1.5 s 后 `--` |
| 四轮胎温 | `0x071..0x074` | 胎温采集模块 | 左栏胎温图 | 无超时 |

上电后所有 CAN 数值都是无效的，收到有效帧才显示；源帧超时或帧内自报无效时回到 `--`，不显示过期值。`0x5A1`（电池侧支路）只解析保存，界面不显示。

### 2. 发送车手屏自己的数据（CANB）

| 内容 | 帧 | 周期 | 用途 |
| --- | --- | --- | --- |
| GPS 车速 | `0x301` | 50 ms | 给 ECU |
| 经纬度、航迹、双天线航向、定位质量 | `0x067`、`0x068` | 50 ms | 遥测记录 |
| 信号质量、里程、卫星数、圈数 | `0x7A0` | 500 ms，圈数变化立即补发 | 遥测记录 |
| 当前圈、上一圈、最快圈、圈差 | `0x7A1` | 200 ms，圈数变化立即补发 | 遥测记录 |
| 驾驶模式请求（模式色块触摸） | `0x310` | 事件 | 给 ECU；byte0 为 ASCII `0`..`3`，DLC 8 |

数据来自车手屏自己的 UM982 GNSS 接收机，算法见 [GPS、圈速与冲刺](gps_lap.md)。

### 3. 方向盘网关（CAN2 → CANB）

车手屏是方向盘进入整车的唯一通路，并在这里实施两条规则：

| 方向盘的帧 | 车手屏的处理 |
| --- | --- |
| `0x310` 驾驶模式请求 | 计时未锁定时在 CANB 上原样转发；计时中不转发。车手屏模式色块也直接发同格式请求 |
| `0x700` 滑级、`0x701` 圈速计时键、`0x702` 消错键 | 不转发原帧；每收到一个有效帧，合并成一帧 `0x703`（DLC 2：滑级、计时位、清错位）发给 ECU。`0x701/0x702` 同时在本机触发计时和清告警 |

规则的细节和原因见 [方向盘与车手屏](steering_wheel.md)。

## 收发机制概要

- **接收**：硬件 ID 白名单过滤，不在表内的帧不进软件；中断只把帧放进 64 项队列，由 CAN 任务解码，任务至少每 50 ms 唤醒一次检查超时。UI 启动完成前到达的帧直接丢弃。
- **发送**：先进 32 项软件队列，由邮箱空闲中断逐帧送入硬件邮箱。自动重传和自动 bus-off 恢复都开启。
- **优先级**：CAN 仲裁 ID 小者优先。车手屏的慢速纯遥测帧 `0x7A0/0x7A1` 用高 ID，避免压过 BMS 故障等控制帧；`0x067/0x068/0x071..0x074` 的 ID 较低，中央库已决定保持现有 ID，不后移。
- **诊断量**：`g_can_rx_drop_count`、`g_can_rx_invalid_count`、`g_user_can_tx_drop_count`、`g_can_bus_off_count` 是复位清零的 RAM 变量，用调试器查看，见 [CAN 接口](can_interface.md#发送队列与总线故障)。

## 修改规则

- 对外帧（ID、DLC、周期、字段）先在 `vehicle-interfaces` 评审，再改本仓库实现和文档。
- 新增接收 ID 须同步修改 `can.c` 的过滤器数组、[CAN 接口](can_interface.md) 的过滤器表和超时表。
- 方向盘一侧的修改须同步 `Steering_wheel` 仓库，二者在专用总线上没有版本协商。
