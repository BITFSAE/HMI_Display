# CAN 接口

本文是车手屏（DBC 节点名 `Display`）在 CANB 与方向盘总线上的**收发实现说明**。帧的字段、比例、单位和范围以 [`vehicle-interfaces`](https://github.com/BITFSAE/vehicle-interfaces) 的 `can/Vehicle_CanB.dbc` 与 `docs/CANB接口.md` 为准，本仓库不保留 DBC 副本（与本仓库同级存放时路径为 `../vehicle-interfaces/`）。本文只写固件实际收哪些帧、怎么用、超时多久、发哪些帧，以及与中央库尚未对齐的部分。整个网络的分工见 [CAN 网络分工](can_network.md)，方向盘与车手屏的配合见 [方向盘与车手屏](steering_wheel.md)。

物理参数见 [硬件映射](hardware.md)：CAN1 接整车 CANB，CAN2 接方向盘，均 500 kbit/s，标准数据帧。

## 接收流程

1. 硬件过滤器为 ID 白名单（16 位 ID 列表模式），不在表内的帧不进入软件。CAN1 过滤器见下表；新增接收 ID 时必须同步修改 `can.c` 的 `CAN1_RX_MSG_ID_BANK*`。
2. 接收中断每次最多读取 3 帧，丢弃扩展帧、远程帧和 DLC>8 的帧（计入 `g_can_rx_invalid_count`），其余放入 64 项静态队列；队列满时丢新帧并计 `g_can_rx_drop_count`。UI 启动完成前到达的帧直接丢弃。
3. CAN 任务（优先级 26，栈 4 KiB）取帧解码，等待队列最多 100 ms，超时后检查各报文族新鲜度。DLC 短于下表「最小 DLC」的帧丢弃并计入 `g_can_rx_invalid_count`。

全部进入 FIFO0，FIFO1 的接收通知未开启。

| 过滤器 bank | ID |
| --- | --- |
| 0 | `0x4B0`、`0x305`、`0x502`、`0x505` |
| 1 | `0x506`、`0x509`、`0x508`、`0x507` |
| 2 | `0x503`、`0x504`、`0x5A0`、`0x5A1` |
| 3 | `0x4A0`、`0x4A3`（各列两次） |
| 4 | `0x5A2`（列四次） |
| 5 | `0x071`、`0x072`、`0x073`、`0x074` |
| CAN2 bank 14 | `0x310`、`0x700`、`0x701`、`0x702` |

## CAN1 接收（CANB）

轮位统一重映射：DBC 帧内顺序为 RL、RR、FL、FR，界面顺序为 0=LF、1=LR、2=RF、3=RR。

| ID | 最小 DLC | 发送方 | 取用的内容 | 超时 | 备注 |
| --- | :-: | --- | --- | --- | --- |
| `0x4B0` | 7 | BMS | 总压（byte0..1，大端，0.1 V）、电流（byte2..3，大端有符号，0.1 A，充电为正）、SOC（byte4，%） | 2000 ms | byte5 bit0/1/2 分别限定电压/电流/SOC，位为 0 则该项显示 `--`；SOC>100 无效；bit3/4 不影响这三项 |
| `0x4A0` | 8（须等于 8） | BMS | SOP 放电功率上限（byte0..1）、回收功率上限（byte2..3），均小端 0.1 kW；LimitsValid（byte6 bit0） | 300 ms | 须同时满足：版本（byte5）为 2、byte6 保留位为 0、单帧 CRC-8 正确（`sop.c`，样例见中央库 `CANB接口.md` 4.4）。不满足的帧丢弃并计入 `g_can_rx_invalid_count`，不刷新超时；LimitsValid 为 0 时显示 `--`。计数（byte4）车手屏不使用 |
| `0x4A3` | 8（须等于 8） | BMS | SOP 允许放电电流（byte0..1）、允许回充电流（byte2..3），均小端 0.1 A | 1500 ms | 版本（byte7 高 4 位）须为 2，无 CRC；InputHealth（byte6）bit7 为 0 表示 SOP 输入不全有效，此时电流显示 `--`。限制原因、过流归零位、ECU 确认位未使用 |
| `0x305` | 6 | ECU | 方向盘转角（byte0..1，小端有符号，0.1°，界面不用）、油门开度（byte2..3，0.1%，取整数百分比）、油压（byte4..5，小端，0.001 kPa） | 1000 ms | **临时**：刹车条由油压推算，2.1 kPa → 0%、4.9 kPa → 90%，线性并限幅到 0..100（参数见 [配置表](configuration.md)）。刹车与油门同帧，同时超时 |
| `0x502` | 8 | ECU | 四轮实际扭矩（int16，小端，Nm） | 1000 ms | |
| `0x505` | 8 | ECU | 四轮转速（int16，小端，rpm） | 1000 ms | |
| `0x506` / `0x507` / `0x508` | 8 | ECU | 四轮电机 / 逆变器 / IGBT 温度（int16，小端，0.1 ℃，取整数度） | 各 1000 ms | 参与 TMAX |
| `0x503` / `0x504` | 8 | ECU | AMK 故障码（uint32，小端）：`0x503` 为 RL、RR，`0x504` 为 FL、FR | 各 1000 ms | 界面显示低 16 位，非零红色 |
| `0x509` | 5 | ECU | 驱动模式（byte0 高 4 位，有符号）、四轮电机使能（byte2 bit4..7：FR、FL、RR、RL） | 1000 ms（使能） | 模式 0..3 对应 S/Q/C/E；−1 及其他值忽略，界面保持上一个模式 |
| `0x5A0` | 8 | PDM | 低压母线电压（int16，大端，mV）、电流（int16，大端，0.01 A）、功率（uint16，大端，0.1 W） | 1500 ms | 四字段同时为 `0x7FFF/0x7FFF/0xFFFF/0xFFFF` 表示 INA226 离线，显示 `--` |
| `0x5A1` | 8 | PDM | 电池侧电压/电流/功率 | 无 | 已解析保存，界面不显示 |
| `0x5A2` | 8 | FanController | 三路转速（uint16，大端，rpm，byte0..5）、两路实测占空比（byte6、byte7，%） | 1500 ms | 第三路风扇无占空比信号，显示 `--` |
| `0x071..0x074` | 8（须等于 8） | 胎温模块 | 每帧 4 个测点，每点「整数度 + 百分之一度」两字节 | 无 | 周期未在中央库登记，暂无超时 |

TMAX 只统计新鲜的电机/逆变器/IGBT 温度，全部失效时显示 `--`。上电后所有 CAN 数值均为无效，收到有效帧才显示；数据有效性的界面表现见 [仪表盘界面](dashboard_ui.md)。

SOP 只接收 BMS 发的 `0x4A0/0x4A3`，不接收 ECU 的 `0x4A4` 确认，也不做 ECU 那样的计数前进判定和恢复流程，只按帧显示。BMS 在自检、待机、预充、故障保持和充电模式停发这两帧，此时界面显示 `--`；高压接通期间输入无效时 BMS 继续发 `0x4A0`，LimitsValid 为 0，同样显示 `--`。功率和电流是两帧，各自判断新鲜度。字段、比例和位定义以中央库 `docs/CANB接口.md` 第 4 章为准。

界面右栏 PK 行的功率峰值和电流峰值（上电后出现过的最大值）不来自专用帧，由 `0x4B0` 的电压电流计算，见 [仪表盘界面](dashboard_ui.md)。

## CAN2 接收（方向盘）

只接收，不发送。发送方是方向盘按钮板，各控件的作用见 [方向盘与车手屏](steering_wheel.md)。收到后在 CAN1 上转发或合并后发出：

| ID | 处理 |
| --- | --- |
| `0x310` 驾驶模式请求 | byte0 必须为 ASCII `0`..`3`（48..51），否则丢弃。计时模式锁（见 [GPS 与圈速](gps_lap.md)）未生效时，在 CAN1 上以**原 ID 和原 DLC**转发给 ECU；无论是否转发，界面都提交该模式（锁生效时界面弹出 MODE LOCK 告警并拒绝切换） |
| `0x700` 滑级 | byte0 超过 7 则丢弃；否则更新界面滑级，并发送 `0x703` |
| `0x701` 圈速计时键（DBC 名 `RecorderToggle`，沿用旧称） | bit0 的上升沿触发界面的圈速/冲刺计时开关（`Dashboard_UI_RequestLapToggle`），同时置位 `0x703` 的计时位 |
| `0x702` 清错 | bit0 的上升沿触发 `0x703` 的清错位，并清除界面上的全部告警（含排队中的，`Dashboard_UI_RequestAlertClear`）；触摸告警条才是逐条消除 |

上升沿判定：上一帧为 0，或上一个 1 帧距今超过 300 ms（`CAN_BUTTON_REPEAT_GAP_MS`）才算一次新按下，按住期间的重复帧不再触发。按方向盘固件代码，每次按键在松开时只发一个 1 帧，不重复也不发 0 帧（尚无总线抓包），此时 300 ms 就是两次按下的最小间隔；其余判定分支为兼容重复发送和 0 帧而保留。每个有效的 `0x700/0x701/0x702` 帧都会触发一次 `0x703`（按键位仅在上升沿为 1），滑级在收到第一个有效 `0x700` 之前为 0，协议没有「滑级未知」的编码。

## CAN1 发送

| ID | DLC | 周期/触发 | 内容 |
| --- | :-: | --- | --- |
| `0x301` | 2 | 50 ms | GPS 车速，0.1 km/h |
| `0x067` | 8 | 50 ms | 经度、纬度，有符号 int32，1e-7° |
| `0x068` | 8 | 50 ms | 航迹、双天线航向、海拔、有效位和质量等级 |
| `0x7A0` | 8 | 500 ms；圈数变化时立即补发 | GPS 信号质量、里程（0.1 km，24 bit）、最大/平均信噪比、卫星数、圈数 |
| `0x7A1` | 8 | 200 ms；圈数变化时立即补发 | 当前圈、上一圈、最快圈（0.01 s）和差值 |
| `0x703` | 2 | 事件：每收到一个有效 `0x700/0x701/0x702` | byte0 滑级 0..7；byte1 bit0 圈速计时（DBC 名 `RecorderToggle`）、bit1 清错 |
| `0x310` | 透传 | 事件：收到 CAN2 的 `0x310` 且计时模式未锁 | 驾驶模式请求，原样转发 |

`0x301/0x067/0x068/0x7A0/0x7A1` 的字段布局以中央库 `docs/CANB接口.md` 第 10 节为准（Display 已确认，实车联调待完成）。发送节拍为 50 ms，`0x7A0` 每 10 拍、`0x7A1` 每 4 拍，上电第一拍全部发送（`gps.c` `GPS_CAN_STATUS_TICKS`、`GPS_CAN_LAP_TICKS`）。GNSS 的 RMC 超过 500 ms 未更新时，`0x301` 的车速如实报 0；界面则保持最后有效车速 3 s，见 [配置表](configuration.md)。`0x7A0/0x7A1` 使用高 ID（低仲裁优先级），不会压过 SOP、BMS 故障等控制帧。

### 发送队列与总线故障

发送先进入 32 项软件队列，由邮箱空闲中断逐帧送入硬件邮箱。队列满时丢新帧并计 `g_user_can_tx_drop_count`。CAN 控制器开启自动重传和自动 bus-off 恢复：总线繁忙时低优先级帧仲裁失败会自动重发，bus-off 由硬件恢复，`g_can_bus_off_count` 记录次数。无节点应答时（如台架单机）邮箱会持续重试，队列满后丢新帧，总线接上后先发出积压的旧帧。这些计数器都是 RAM 变量，复位清零，可在调试器中查看。
